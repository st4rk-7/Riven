# Local PostgreSQL setup — RIV-15

This slice adds schema, migrations, Better Auth sessions and retailer-scoped
HTTP routes. The frontend still displays its labelled demo until Dilsan connects
the new endpoints. Real-browser extension verification remains pending.

## Create local databases

PostgreSQL 18 is the verified local version. In the project root:

```powershell
createdb -h 127.0.0.1 -p 5432 -U postgres riven_dev
createdb -h 127.0.0.1 -p 5432 -U postgres riven_test
```

If either database already exists, keep it and continue. Do not drop an
existing database to repeat these steps.

Create a local `.env` using `.env.example`, or add the two database variables
to an existing `.env`. Replace the placeholder passwords locally. Passwords
in URLs must be percent-encoded; for example `@` becomes `%40` and `#` becomes
`%23`. Never commit `.env`. These local examples use the PostgreSQL installation
account; hosted operation needs a dedicated role with suitable permissions.

```powershell
npm.cmd ci
npm.cmd run db:migrate
npm.cmd run db:check
npm.cmd run auth:setup
npm.cmd run typecheck
npm.cmd test
npm.cmd run test:integration
```

`db:migrate` uses DATABASE_URL. It applies numbered SQL files in a transaction,
serializes concurrent runs, records checksums in schema_migrations and skips
unchanged applied files. A failure rolls back the whole run. Add a new migration
for changes; never edit an already applied migration. There is no destructive
automatic reset or down command.

`db:check` uses TEST_DATABASE_URL and refuses a database name not ending in
`_test`. It applies migrations to that separate database, verifies reruns and
the Better Auth schema, then tests constraints with synthetic records inside
a rolled-back transaction. The test database retains its schema and migration
history, but none of those synthetic test records.

## Tables and ownership

- retailers is the tenant/workspace. It contains no login passwords.
- Better Auth's user table belongs to a retailer through retailerId.
- Better Auth's session and account tables belong to a user. Credential hashes
  belong to account.password and must be generated by Better Auth's APIs.
- verification is part of Better Auth's core schema.
- products, observations and attempts each have a required retailer_id.
- An observation or attempt may have product_id NULL. Its retailer_id remains
  required. This preserves ownership for unmatched and failed collection.
- Composite foreign keys reject linking a retailer's observation or attempt to
  another retailer's product. Deleting a referenced product is refused rather
  than silently erasing history. No product-deletion API is delivered here.
- Money is decimal text plus currency, matching the shared API schema; unknown
  prices remain NULL. Timestamps are timestamptz and API responses use UTC.

The four core authentication tables were generated using Better Auth 1.7.11's
`getMigrations(...).compileMigrations()` with server/auth-options.ts. Only the
retailers table and retailer foreign key/index were added around that output.
The database check compares the live schema with that same library configuration.

The auth configuration disables public sign-up and marks retailerId as a
server-managed field. RIV-18 seed accounts need a retailers row, a user row with
retailerId, and an account row with providerId = 'credential', accountId = user.id
and userId = user.id. Generate account.password using hashPassword from
better-auth/crypto; do not invent a password format. The integration test shows
this process using throwaway accounts, then removes them.

Database constraints do not filter SELECT queries. Protected routes derive the
retailer from the verified session and scope every read/write by that identity.
An observation and its successful attempt use one database transaction.

## Server and browser configuration

`npm run auth:setup` generates a random BETTER_AUTH_SECRET inside the ignored
local .env and preserves an existing secret. It does not print secrets. Keep the
secret stable across server restarts; changing it invalidates existing cookies.
The dev server automatically loads .env. Missing database or secret settings
prevent startup instead of falling back to unauthenticated records.

Defaults are BETTER_AUTH_URL=http://127.0.0.1:3000 and
WEB_ORIGIN=http://127.0.0.1:5173. Production requires HTTPS. Public sign-up is
disabled; no credentials are written into source code or frontend storage.
Do not mix localhost and 127.0.0.1 when signing in because cookies are host-bound.

For the extension, load the unpacked build and copy its exact 32-character ID
from chrome://extensions into RIVEN_EXTENSION_ORIGIN=chrome-extension://THE_ID.
Rebuild the popup with `npm run build:extension`, then reload the unpacked extension.
Restart the server after changing that setting. Only this extension origin is
allowed; a wildcard is deliberately not used. Requests include credentials and
use the current profile's session cookie. Chrome's host-permission and cookie
settings still require an actual browser walkthrough with the account screen.

Browser POST requests require a trusted Origin. A non-browser client with no
Origin must send X-Riven-Client: riven. Read docs/api.md for request/error shapes.
Session cookies are HttpOnly, SameSite=Lax and Secure when the API uses HTTPS.
Sessions have a fixed 24-hour lifetime and sign-out revokes the database session.

## Integration tests

`npm run test:integration` loads TEST_DATABASE_URL from .env and fails if it is
missing. Tests refuse a database name not ending in _test, migrate that database,
create two synthetic retailers/users/products, exercise the actual Fastify
routes with real Better Auth cookies, and clean up only their own records.
They check ownership, invalid/expired/revoked sessions, CSRF/origin restrictions,
login throttling, persistence and rollback when recording the success attempt
fails. A short-lived trigger is used only in the isolated test database for the
rollback check and is removed in a finally block.

`npm test` runs the integration suite only when TEST_DATABASE_URL is already in
the environment. Otherwise it reports those cases as skipped. CI provisions
PostgreSQL and sets that variable, so the full suite runs on pull requests.
These API tests do not prove a completed frontend or Chrome walkthrough.

The login limiter is process-local; a multi-process deployment needs a shared
limiter. Public deployment and browser verification are separate acceptance work.
